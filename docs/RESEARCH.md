# От одного писка до Speaker Studio

Я хотел простую вещь: заставить маленькую пищалку материнской платы звучать по команде из Windows. Потом захотел проиграть через неё мелодию. Из этого вырос Speaker Studio — плеер с MIDI, CSV, локальной MP3-транскрипцией, настройкой ритма и графиком частот.

По дороге пришлось разобраться с тремя разными задачами: как добраться до физического speaker, какие ноты выбрать из записи и как вовремя их переключать. Здесь рассказываю, что пробовал и к чему пришёл. Устройство кода вынесено в [ARCHITECTURE.md](ARCHITECTURE.md).

Результаты ниже — состояние проекта на 2 октября 2026 года. Обозначения E09–E25 — номера опытов в моём рабочем журнале.

## 1. Первые попытки: пищалка молчала, колонки пищали

Начал я с очевидного `Beep`. Команда выполнялась, но звук шёл через колонки монитора. Для моей задачи этого было мало: нужен был именно speaker в корпусе.

Оказалось, что начиная с Windows 7 `Beep` направляет сигнал на звуковое устройство по умолчанию для сеанса. Имя функции осталось привычным, а путь вывода изменился. Это описано в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/utilapiset/nf-utilapiset-beep).

Следующий шаг — [InpOut](https://www.highrez.co.uk/downloads/inpout32/). Через DLL можно читать и писать I/O-порты; доступ обеспечивает её kernel driver. Поэтому физический режим запускается с правами administrator. На тестовом ПК пищалка заработала, и появился рабочий способ задавать частоту и длительность.

Так я отказался от идеи обойтись одним стандартным `Beep`. Звук при POST был полезной проверкой самой пищалки, но доступ к ней из Windows пришлось проверять отдельно: он зависит и от платы, и от допуска драйвера системой.

## 2. Четыре операции, которые создают тон

В legacy PC тон генерирует PIT — Programmable Interval Timer. Я использую его channel 2 в mode 3, то есть генератор прямоугольного сигнала. Отдельные биты gate включают подачу сигнала на speaker.

В [SpeakerOutput](../speaker-player/src/Playback.cs) последовательность короткая:

| Порт | Что записываю |
| --- | --- |
| `0x43` | `0xB6`: channel 2, mode 3, binary count, сначала low byte, затем high byte |
| `0x42` | Младший и старший байты делителя |
| `0x61` | Устанавливаю младшие два бита, сохраняя остальные |
| `0x61` при остановке | Очищаю младшие два бита |

Частота получается делением clock на целое число:

```text
clockHz = 1 193 182
count = clamp(round(clockHz / requestedFrequency), 2, 65536)
actualPitFrequency = clockHz / count
```

Для mode 3 допустимы counts от 2 до 65536. Максимальный binary count записывается как два нулевых байта — это специальное представление 65536, а не выключение генератора. Диапазон и режим описаны в [Intel 8254, Figure 22](https://www.cs.cmu.edu/~410/doc/8254.pdf).

Из этих чисел получается примерно **18,2 Гц — 596,6 кГц**. Это диапазон делителей таймера. Акустический диапазон пищалки гораздо интереснее: на него влияют излучатель, резонанс и схема подключения. Я не измерял звук на краях этого диапазона.

Ранний предел 100–10000 Гц оказался ограничением программы, а не InpOut. Я убрал его. При этом частота всё равно округляется целым делителем, а график показывает запрошенные события, не измерение на пинах.

### А можно сделать тише?

Я тоже хотел ползунок громкости. Но через выбранный PIT/gate путь доступны делитель и включение сигнала, отдельного регистра аналоговой амплитуды здесь нет. Переписать DLL недостаточно: она лишь обращается к существующим портам. [Intel: регистр offset 61](https://edc.intel.com/content/www/ru/ru/design/products-and-solutions/processors-and-chipsets/comet-lake-u/intel-400-series-chipset-on-package-platform-controller-hub-register-database/1.2/nmi-status-and-control-nmi-sts-cnt-offset-61/).

В плеере есть «Звук, %», но это время звучания внутри клетки ритма. Я оставил такое название и не выдаю его за управление напряжением. Аппаратное ослабление можно исследовать после определения типа speaker и схемы; для внешне возбуждаемого piezo такие подходы описывает [Murata](https://www.murata.com/en-global/support/faqs/sound/diaphragm/char/sch0001).

## 3. Из MP3 я получаю ноты, а затем выбираю одну линию

Когда одиночный тон стал управляемым, захотелось музыки. Тут быстро обнаружилась разница форматов:

| Формат | Что в нём находится |
| --- | --- |
| MP3/WAV после декодирования | Значения звукового сигнала во времени |
| MIDI | Начала и концы нот, высоты, партии и другие музыкальные события |
| Speaker CSV | Одна частота, длительность и пауза для каждого шага |

Мой текущий путь выглядит так:

```mermaid
flowchart LR
    A[MP3 / WAV] --> B[Декодирование]
    B --> C[MuScriptor: события нот]
    C --> D[Полный MIDI с партиями]
    D --> E[Выбор партии и одного голоса]
    E --> F[frequency / duration / pause]
    F --> G[PIT: прямоугольный сигнал]
```

Пищалка держит одну управляемую высоту за раз. У прямоугольного сигнала есть гармоники, но это всё ещё один задаваемый тон. Сохранить несколько инструментов, вычислив одну «дельту частот», не получается: пропадут их амплитуды, фазы и форма общего сигнала.

Я смотрел и на другой путь — быстрые импульсы для воспроизведения waveform. В Linux так работает отдельный драйвер [snd-pcsp](https://github.com/torvalds/linux/blob/master/sound/drivers/pcsp/pcsp_lib.c) с kernel hrtimer. В моём E09 были расчёты 1-bit/PDM и проверки запуска wrappers; до физического опыта с этим способом я не дошёл. Поэтому в текущем плеере используется последовательность тонов.

### Почему остановился на MuScriptor Small

Мне понравился MIDI, полученный через [MuScriptor](https://github.com/muscriptor/muscriptor), и я добавил локальную ветвь с Small. Конкретный checkpoint веб-сервиса для того MIDI я не установил; локальная модель — самостоятельный вариант для сравнения.

MuScriptor предсказывает ноты и инструменты по mel-spectrogram. В зафиксированной версии это mono 16 кГц и фрагменты по 5 секунд. Prelude переносит состояние удерживаемых нот между фрагментами. [Исходник использованной версии](https://github.com/muscriptor/muscriptor/blob/7f213afecf23bd6a1b8672aa223690ee9807cefb/muscriptor/transcription_model.py).

В моём converter параметры заданы явно:

```text
CPU + local weights
batch_size = 1
cfg_coef = 1
prelude_forcing = True
greedy decoding
```

Полный MIDI сохраняет партии и percussion. Уже при подготовке speaker-последовательности я исключаю percussion и выбираю один голос. Velocity при экспорте равна 64, так что динамика исполнения в этой цепочке не восстанавливается. Модель включена в [релиз 2.0.1](https://github.com/esinkirill/speaker-studio/releases/tag/v2.0.1); её подключение описано в [MODEL.md](MODEL.md). Веса Small имеют CC BY-NC 4.0 — условия находятся в [model card](https://huggingface.co/MuScriptor/muscriptor-small).

## 4. Верхняя нота — ещё не главная мелодия

Первый понятный selector: играть верхнюю активную ноту выбранной партии. Нет активных нот — REST. Повторная атака этой же высоты остаётся отдельной нотой; событие более низкого сопровождения не разрывает удерживаемый верхний голос.

Так получается воспроизводимая линия. Но верхняя нота может быть сопровождением, гармоникой или ошибкой распознавания. Поэтому я сохраняю полный MIDI: выбор голоса можно менять, не повторяя аудиотранскрипцию.

В E22 я нашёл 85 пар с общим началом и интервалом 19 полутонов:

```text
2^(19/12) ≈ 2,996614
```

Это почти третья гармоника. Соблазнительно было удалить все такие пары. Но совпадение атак и частот бывает и у настоящих музыкальных партий. Я оставил это гипотезой для проверки, а не универсальным фильтром.

FFT peak тоже не отвечает на вопрос «какая это нота главной мелодии?». Для ответа нужны размеченные pitch/onset/offset события. Для их сопоставления полезен [mir_eval transcription](https://github.com/mir-evaluation/mir_eval/blob/main/mir_eval/transcription.py).

## 5. BPM: число, доли и место первой клетки

Следующей проблемой стал ритм. Я сначала смешивал изменение скорости с определением BPM, хотя это разные операции.

Source BPM описывает исходный трек. Desired BPM задаёт, как быстро его проиграть. Музыкальная сетка делит долю на равные части, а phase определяет положение клеток на таймлайне:

```text
speed = desiredBpm / sourceBpm
sourceStepMs = 60000 / sourceBpm / partsPerBeat
playbackStepMs = sourceStepMs / speed
grid[k] = phaseMs + k × sourceStepMs
```

Здесь доля — четверть. При 120 BPM и четырёх частях четверти шаг составляет 125 мс, то есть шестнадцатую ноту. Деление 16 даёт 1/64. В плеере есть части 1, 2, 3, 4, 6, 8, 12 и 16, включая триоли.

Для аудио я использую Essentia `RhythmExtractor2013`. Он возвращает BPM, времена долей и confidence. Confidence полезен как показатель алгоритма, но не является вероятностью правильного темпа; возможны половинный и двойной BPM. [Документация алгоритма](https://essentia.upf.edu/reference/std_RhythmExtractor2013.html).

В E20 короткий участок дал 47 долей: raw 145,1553 BPM, fit 145,9855 BPM, RMS 5,537 мс. Полная запись длиной около 233,718 секунды дала близкий fit — 145,9550 BPM, но RMS уже 77,555 мс и максимум 861,257 мс. Одного среднего BPM оказалось мало для ровной сетки длинного трека.

Ещё одна находка — `muscriptor:bar_offset`. Внешний MIDI мог добавлять тишину для выравнивания тактов. В моём примере offset 1,2634 секунды объяснял большую часть различия длительностей. Я сохраняю этот marker для сравнения с аудио, не вычитая его из каждого MIDI по умолчанию. Логика выравнивания есть в [MuScriptor beats.py](https://github.com/muscriptor/muscriptor/blob/7f213afecf23bd6a1b8672aa223690ee9807cefb/muscriptor/utils/beats.py).

## 6. Разделение нот, сетка и плавный переход

Мне хотелось, чтобы соседние ноты различались чётче, и одновременно хотелось плавных переходов. Для этого я разделил несколько настроек:

| Настройка | Как меняет события |
| --- | --- |
| Тон, полутоны | `f' = f × 2^(n/12)`, время остаётся тем же |
| Скорость | Масштабирует абсолютные временные границы |
| Note gap | Вырезает тишину из конца ноты |
| Quantize | Сдвигает внутренние границы на 50% к ближайшей клетке |
| Chop | Оставляет звук только в звучащей части каждой клетки |
| Glide | Добавляет переход высоты в начале следующей соседней ноты |

Общая длина после эффектов остаётся равной длине исходника, делённой на скорость. Quantize сохраняет порядок и тип REST, но может менять длину пауз; совсем короткий интервал иногда исчезает при округлении до миллисекунд.

### Ошибка с дополнительными паузами

Первоначально я добавлял gap поверх ноты — и трек постепенно удлинялся. В E19 поменял правило: пауза берётся из самой ноты, после масштабирования времени.

```text
G = min(requestedGap, max(0, D − 1))
tone = D − G
pause = P + G
```

Для `D=100`, `P=20`, `G=10` получаются 90 мс звука и 30 мс тишины. Сумма всё ещё 120 мс, следующая нота начинается вовремя. REST дополнительный gap не получает.

### Почему glide идёт по логарифму частоты

Октава — это удвоение частоты. Поэтому переход я считаю в log-frequency, а гладкую форму задаю cubic smoothstep:

```text
u ∈ [0, 1]
s(u) = 3u² − 2u³
f(u) = exp(log(f0) + (log(f1) − log(f0)) × s(u))
```

Переход занимает начало следующей ноты, не увеличивая её длительность. Первый и последний шаги соответствуют соседним высотам. Реализация состоит из коротких удерживаемых частот с шагом 5/10/20/50 мс.

Glide не проходит через настоящую паузу, REST или gap. Я применяю его до Chop: искусственные разрывы gate не должны стать новыми музыкальными атаками.

Все эти операции собраны в [SequenceTiming.cs](../speaker-player/src/SequenceTiming.cs). График, проигрывание и сохранённый CSV используют один расчёт. Иначе легко получить красивую диаграмму одного трека и звучание другого.

Разбить строку на сто одинаковых строк можно, но музыкальной информации от этого не прибавится. Grid меняет артикуляцию, glide создаёт выбранный переход; частота дискретизации MP3 при этом не повышается.

## 7. Таймер: короткие задержки умеют складываться

Ещё одна ошибка оказалась совсем программной. Если для каждой ноты ждать её длительность, а затем выполнять работу следующей, расходы на output и UI незаметно добавляются к каждой строке.

Я перешёл к абсолютным границам и одному monotonic clock:

```text
newBoundary[k] = round(sourceBoundary[k] / speed)
newDuration[k] = newBoundary[k+1] − newBoundary[k]
newTotal = round(sourceTotal / speed)
```

Так решаются две проблемы: отдельно округлённые миллисекунды не накапливаются, а ожидание идёт до конца сегмента на общем таймлайне. Пользовательская pause исключается из clock. Seek меняет позицию, сохраняя backend и paused state.

`Stopwatch` хорошо измеряет время, но Windows scheduling всё ещё может опоздать: короткая нота получит меньше времени или будет пропущена. Я проверяю clock и переходы тестами; реальный timing на speaker нужно измерять отдельно. [Microsoft: high-resolution timestamps](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps), [Sleep и scheduling](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-sleep).

Перемотка добавила ещё одну тонкость: старый progress callback может стоять в UI очереди уже после seek. Поэтому у каждого запуска есть `SessionId`, а у каждой смены позиции — `PositionRevision`. Проверка выполняется внутри UI callback. Подробный пример этой гонки — в [архитектуре](ARCHITECTURE.md).

## 8. 144 варианта: что я сравнивал

Чтобы понять, где теряется мелодия, я сделал большую матрицу на одном участке около 19,475 секунды. Менял распознавание, предварительное разделение аудио и способ выбора одного голоса.

| Семейство | Базовых / контрольных вариантов | Что менял |
| --- | ---: | --- |
| MIDI и его проекции | 7 | Верхний, нижний, median и continuity/harmonic-aware голос |
| Спектральные методы | 12 | Каналы, harmonic salience, DP, фиксированные templates, HPSS |
| Melodia | 5 | Три extractor runs и варианты очистки |
| Basic Pitch ONNX | 14 | 8 canonical runs и 6 decoder controls |
| YourMT3 | 10 | 5 checkpoints, прямой запуск и сдвинутая сетка окон |
| MuScriptor Small | 4 | Default, shift, отключение prelude, CFG 2 |
| Consensus | 2 | Пересечение событий двух запусков |
| **Базовых / контрольных** | **54** | |
| Производные mono selectors | **90** | Highest, lowest, harmonic DP для 30 polyphonic candidates |
| **Всего** | **144** | |

[Demucs](https://github.com/facebookresearch/demucs) здесь разделял аудио на stems, а [Basic Pitch](https://github.com/spotify/basic-pitch) распознавал нотные события. Это разные этапы. Stem `other` я пробовал как вход, но само его название не означает выделенную главную мелодию.

Спектральный вариант с Gaussian templates и неотрицательными коэффициентами я называю fitting при фиксированном `W`. Это важно для понимания опыта: templates заданы заранее, поэтому это не blind learned NMF. Гладкая линия и маленький остаток реконструкции сами по себе не выбирают нужный музыкальный голос.

### Я сначала проверил, что сравниваю правильно сохранённые файлы

| Результат E23 | Количество / значение |
| --- | --- |
| Variant MIDI | 144 |
| Preview WAV | 144 |
| Speaker CSV | 113 |
| Структурные assertions независимого reader | 258725 |
| Потерянные / лишние файлы в финальном inventory | 0 / 0 |
| Незавершённые ноты и same-pitch/channel overlaps | 0 |
| Длительность каждого speaker CSV | 19475 мс |

Speaker CSV меньше, чем MIDI: для части polyphonic вариантов я сохранял отдельные mono projections, а не самостоятельный CSV исходного варианта.

Первый промежуточный пакет не прошёл inventory check: после переименования decoder controls остались stale файлы. Я пересобрал его в пустой каталог и прочитал заново. Так удалось убрать ошибку упаковки из сравнения алгоритмов.

### Agreement оказался полезнее количества нот

Я сдвигал аудио и сравнивал два предсказания одной модели: одинаковый pitch и onset в пределах 50 мс, в строгом варианте — ещё и offset. Получилось такое onset agreement F1:

| Модель / конфигурация | F1 |
| --- | ---: |
| YourMT3 Single | 0,890 |
| YourMT3 T5 | 0,535 |
| YourMT3 MoE | 0,461 |
| YourMT3 MultiPS | 0,664 |
| YourMT3 MoEPS | 0,333 |
| MuScriptor Small | 0,685 |

Это устойчивость к контексту и разбиению, а не точность относительно нотной разметки. Два запуска могут согласованно ошибаться. Consensus оставил 71 из 96 событий Single и 110 из 197 MuScriptor; правильность удаления остальных я ещё не оценил по reference.

Из этого опыта я вынес простое правило: больше нот, ровнее график или меньше переключений — удобные признаки для просмотра результата, но ими нельзя автоматически выбрать лучший transcriber.

### Самая неприятная находка в переносимости

Я запускал Python с изоляцией окружения и `PATH` только из системного каталога. Модель загружалась. Казалось, runtime собран полностью.

Но Windows DLL loader всё равно подхватил отсутствующий в комплекте `msvcp140.dll` из системы. В локальном комплекте E25 я добавил app-local MSVC 14.51.36231.0 и проверил ordinary/delay imports 83 Python native images, отдельно Node/FFmpeg. В новом процессе все три VC14 DLL реально загрузились из комплекта; Microsoft signatures были Valid. После этого повторил C# smoke.

Для публичного 2.0.1 я выбрал профиль с установленным системным VC14 x64: его получают через официальный installer Microsoft. Модель, Python CPU runtime и Node включены в архив. `Prepare-Audio.cmd` отдельно скачивает фиксированную сборку FFmpeg от BtbN и Essentia.js, проверяет контрольные суммы архивов и сохраняет их рядом с приложением. После подготовки конвертация работает локально; порядок запуска описан в [MODEL.md](MODEL.md).

В builder это отражено явно: профиль по умолчанию — `system-vc14`, а `--vc-runtime` включает прежний вариант `app-local-vc14`. Так прежний опыт с автономным комплектом остаётся в истории, а инструкция нового релиза соответствует его фактическим prerequisites.

Чистая Windows VM — следующий опыт: он должен проверить переносимость за пределами моего host. Проверки свежего public clone и команды для программных тестов описаны в [VERIFICATION.md](VERIFICATION.md).

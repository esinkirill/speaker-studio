# Музыка на пищалке материнской платы

Мне хотелось заставить маленькую пищалку в корпусе ПК звучать по команде из Windows, а затем проиграть через неё мелодию. Из этой задачи вырос Speaker Studio. Для этого пришлось связать три вещи: управление аппаратным генератором, выбор нот из музыки и расписание их переключения.

## Почему обычный Beep не помог

Первые попытки через `Beep` давали звук из колонок монитора. Начиная с Windows 7 эта функция передаёт тон на звуковое устройство по умолчанию для сеанса — так описан её современный путь в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/utilapiset/nf-utilapiset-beep).

Физический PC speaker использует другой аппаратный путь. В проекте доступ к его I/O-портам обеспечивает [InpOut](https://www.highrez.co.uk/Downloads/InpOut32/): приложение вызывает DLL, а операции выполняет её kernel driver. Для этого нужны права administrator и плата, на которой соответствующий путь подключён к speaker. Писк при POST подтверждает, что сама пищалка способна звучать; доступ к ней из Windows зависит также от драйвера и платформы.

## Как PIT создаёт тон

В legacy PC за этот сигнал отвечает PIT — Programmable Interval Timer. Channel 2 в mode 3 генерирует прямоугольную волну. Программа задаёт делитель, а gate включает или выключает сигнал на speaker.

Последовательность в [SpeakerOutput](../speaker-player/src/Playback.cs) состоит из нескольких записей:

| Порт | Действие |
| --- | --- |
| `0x43` | Записать `0xB6`: channel 2, mode 3, binary count, low byte затем high byte |
| `0x42` | Записать младший и старший байты делителя |
| `0x61` | Установить младшие два бита, сохранив остальные |
| `0x61` при остановке | Очистить младшие два бита |

Частота задаётся через целочисленный делитель:

```text
clockHz = 1 193 182
count = clamp(round(clockHz / requestedFrequency), 2, 65536)
actualPitFrequency = clockHz / count
```

В mode 3 допустимы counts от 2 до 65536. Значение 65536 записывается двумя нулевыми байтами. Это специальное представление максимального binary count. Диапазоны режимов приведены в [Intel 8254, Figure 22](https://www.cs.cmu.edu/~410/doc/8254.pdf).

Такой диапазон делителей даёт примерно **18,2 Гц — 596,6 кГц**. Излучатель имеет собственные резонансы и акустический диапазон, поэтому крайние значения таймера не означают полезный или слышимый звук. Раннее ограничение 100–10000 Гц было задано программой и было убрано. Точность всё равно ограничена целым делителем; диаграмма плеера показывает запрошенные частоты.

### Частота, тембр и громкость

Идеальная прямоугольная волна содержит основную частоту и нечётные гармоники `3f`, `5f`, `7f` и далее. Они участвуют в её характерном тембре. При этом в выбранном режиме PIT доступен один делитель: нельзя независимо задать высоты и амплитуды нескольких инструментов.

Сведение многоголосной записи в единственную «дельту частот» потеряет информацию о форме сигнала. Сумма двух волн содержит обе составляющие, их амплитуды и фазы. Для воспроизведения самой waveform нужен иной способ управления импульсами. Пример такого подхода — Linux driver [snd-pcsp](https://github.com/torvalds/linux/blob/master/sound/drivers/pcsp/pcsp_lib.c), использующий kernel hrtimer. Speaker Studio работает с последовательностью удерживаемых тонов.

Через PIT/gate доступны частота и включение сигнала. Отдельной настройки аналоговой амплитуды у выбранных регистров нет; переписывание InpOut не добавит её. Назначение битов порта `0x61` описано в [Intel NMI Status and Control](https://edc.intel.com/content/www/ru/ru/design/products-and-solutions/processors-and-chipsets/comet-lake-u/intel-400-series-chipset-on-package-platform-controller-hub-register-database/1.2/nmi-status-and-control-nmi-sts-cnt-offset-61/). Параметр «Звук, %» в плеере задаёт долю времени звучания внутри ритмической клетки. Он меняет артикуляцию, а аппаратный регулятор напряжения в проекте не реализован.

## От записи до одной музыкальной линии

Для воспроизведения мелодии нужна последовательность высот и времён. Форматы описывают разные уровни этой задачи:

| Формат | Содержимое |
| --- | --- |
| MP3/WAV после декодирования | Значения звукового сигнала во времени |
| MIDI | Начала и концы нот, высоты, партии и музыкальные события |
| Speaker CSV | `frequency` в Гц, `duration` и `pause` в мс |

```mermaid
flowchart LR
    A[MP3 / WAV] --> B[Декодирование]
    B --> C[MuScriptor: события нот]
    C --> D[MIDI с партиями]
    D --> E[Выбор партии и одного голоса]
    E --> F[frequency / duration / pause]
    F --> G[PIT: прямоугольный сигнал]
```

Локальный конвертер использует MuScriptor Small. Модель получает mel-spectrogram, предсказывает события нот и инструментальные группы. В [использованной версии](https://github.com/muscriptor/muscriptor/blob/7f213afecf23bd6a1b8672aa223690ee9807cefb/muscriptor/transcription_model.py) вход — mono 16 кГц, обработка идёт фрагментами по 5 секунд. Prelude переносит состояние удерживаемых нот между фрагментами.

В [transcribe-midi.py](../speaker-player/converter/transcribe-midi.py) заданы CPU, `batch_size=1`, `cfg_coef=1`, `prelude_forcing=True` и greedy decoding. Полученный MIDI сохраняет полифонию, партии и percussion. Velocity равна 64: модель не предсказывает динамику исполнения. Подключение модели описано в [инструкции по интеграции](MODEL.md).

Для speaker из выбранной партии берётся верхняя активная нота, percussion исключается. При отсутствии активных нот получается REST. Повторная атака той же высоты остаётся отдельным событием; начало нижней ноты сопровождения не разрывает удерживаемый верхний голос. Формат результата описан в [справочнике CSV](CSV_FORMAT.md).

Такой selector прост и воспроизводим, но верхний голос может оказаться сопровождением или ошибкой транскрипции. Поэтому полный MIDI сохраняется до редукции: другой голос можно выбрать без повторного распознавания аудио.

### Почему нельзя автоматически вычеркнуть гармоники

В одном из полученных MIDI нашлось 85 пар нот с общим началом и расстоянием 19 полутонов:

```text
2^(19/12) ≈ 2,996614
```

Этот интервал почти совпадает с третьей гармоникой. В искажённом сигнале transcriber может принять гармонику за самостоятельную ноту. Но похожее сочетание бывает и у настоящих партий, например при октавном и квинтовом удвоении. Удаление всех таких пар способно убрать нужные ноты.

По той же причине самый сильный FFT peak не определяет главную мелодию. Для оценки нужны высота, onset и offset музыкальных событий; [mir_eval transcription](https://github.com/mir-evaluation/mir_eval/blob/main/mir_eval/transcription.py) показывает, как сопоставлять такие события с разметкой.

## Что показало сравнение 144 вариантов

На одном фрагменте длительностью около **19,475 секунды** были сравнены 54 базовых и контрольных результата и 90 производных mono-проекций. Всего получилось 144 варианта. Менялись три этапа: подготовка аудио, распознавание нот и выбор одного голоса.

| Подход | Что он должен был прояснить |
| --- | --- |
| Highest, lowest, median и continuity/harmonic-aware MIDI selectors | Насколько результат зависит от выбора голоса после транскрипции |
| Спектральная salience, DP, HPSS и фиксированные harmonic templates | Можно ли удерживать одну высоту, учитывая гармоники и непрерывность |
| Melodia и варианты очистки | Откуда берутся короткие вставки и пропуски в одной линии pitch |
| Basic Pitch на mix и Demucs stems | Помогает ли предварительное разделение инструментов |
| Пять checkpoints [YourMT3](https://huggingface.co/spaces/mimbres/YourMT3), MuScriptor Small и сдвиги окон | Насколько transcriber зависит от контекста и разбиения записи |
| Consensus двух запусков | Что теряется, если оставлять только согласованные события |

Это сравнение способов обработки; текущая ветвь MP3 → MIDI в приложении использует MuScriptor Small. Остальные методы были нужны для изучения ошибок и выбора подхода.

### Очистка помогает только после распознавания

У Melodia без очистки звучащая часть занимала 9,014 секунды из 19,475, после стандартной очистки — 8,550 секунды. Количество событий изменилось с 75 до 37. Значительная часть пропусков уже была в исходном pitch track, поэтому одной настройкой cleaner восстановить всю мелодию не удалось. Более мягкий cleaner сохранял 48 событий — полезный вариант для сравнения, но само количество нот не говорит об их правильности.

[Demucs](https://github.com/facebookresearch/demucs) разделял запись на stems, а [Basic Pitch](https://github.com/spotify/basic-pitch) превращал выбранный вход в ноты. При одинаковых default параметрах Basic Pitch дал 172 события на полном mix и 170 на stem `other`. Получение stem с таким названием ещё не гарантирует выделения ведущей партии. Сокращение minimum note length увеличивало эти числа до 211 и 205; оно также сохраняло больше коротких кандидатов.

Отдельно сравнивались декодеры. FFmpeg и Soundfile дали одинаковое количество PCM frames и нулевой временной сдвиг; результаты Basic Pitch совпали по высотам, времени и velocity. Это помогло исключить выбор этих двух декодеров как причину различия нот. В ветви Demucs другой загрузчик добавлял около 12 мс, поэтому для сравнения основных алгоритмов использовался общий декодированный вход.

Спектральная salience оценивает поддержку высоты по нескольким её гармоникам. Dynamic programming (DP) выбирает путь высот во времени, учитывая эту поддержку и цену скачков между соседними участками. Цена скачков управляет склонностью алгоритма удерживать высоту.

Другой спектральный вариант, fitting, использовал заранее заданные Gaussian harmonic templates `W` и неотрицательные коэффициенты `H`:

```text
X ≈ W × H, H ≥ 0
```

Здесь `W` фиксирована, поэтому метод подбирает активность заданных шаблонов. Маленький остаток реконструкции и гладкий pitch path показывают свойства этого подбора, но ещё не идентифицируют нужный музыкальный голос. Стабильное сопровождение тоже может дать гладкую линию.

### Сдвиг окон меняет распознанные ноты

Сравнение повторялось со сдвигом аудио, после которого события возвращались на исходный таймлайн. У MuScriptor Small прямой запуск дал 197 тональных событий, а запуск со сдвигом 2,5 секунды — 124. Разница затронула и середину фрагментов: влияние контекста не ограничилось местами склейки.

Для сравнения двух запусков сопоставлялись события одинаковой высоты с onset в пределах 50 мс, одно событие с одним. Если `M` — количество совпадений, а `N1` и `N2` — количества событий, onset agreement считается так:

```text
F1 = 2 × M / (N1 + N2)
```

| Модель / конфигурация | Onset agreement F1 |
| --- | ---: |
| YourMT3 Single | 0,890 |
| YourMT3 T5 | 0,535 |
| YourMT3 MoE | 0,461 |
| YourMT3 MultiPS | 0,664 |
| YourMT3 MoEPS | 0,333 |
| MuScriptor Small | 0,685 |

Эти значения описывают устойчивость к изменению контекста на выбранном фрагменте. Уверенно повторённая ошибка тоже увеличит agreement; сравнения с эталонной нотной разметкой здесь нет.

Consensus добавлял требование совпадения offset и оставлял события прямого запуска без усреднения границ. Он сохранил 71 из 96 событий YourMT3 Single и 110 из 197 MuScriptor. Такой фильтр убирает нестабильные кандидаты, но способен удалить и верную ноту. Использовать его как автоматический критерий качества пока оснований нет.

## BPM требует долей и их положения

В CSV уже есть длительности в миллисекундах, но по ним нельзя однозначно восстановить BPM: интервал 200 мс может быть четвертью при 300 BPM или восьмой при 150 BPM. Нужны сведения о музыкальных долях. MIDI содержит tempo map; при её изменениях события пересчитываются с учётом каждого участка.

Source BPM описывает исходное время, desired BPM задаёт скорость проигрывания. Для равномерной сетки также нужны деление доли и phase — положение клеток на таймлайне:

```text
speed = desiredBpm / sourceBpm
sourceStepMs = 60000 / sourceBpm / partsPerBeat
playbackStepMs = sourceStepMs / speed

grid[k] = phaseMs + k × sourceStepMs
```

Доля здесь — четверть. При 120 BPM и четырёх частях четверти шаг равен 125 мс: шестнадцатая нота. Деление 16 даёт 1/64. Триоли получаются при 3, 6 или 12 частях.

Для аудио используется Essentia [RhythmExtractor2013](https://essentia.upf.edu/reference/std_RhythmExtractor2013.html). Он возвращает BPM, времена найденных долей и confidence. Возможны половинный и двойной BPM; confidence служит показателем алгоритма, его нельзя читать как вероятность правильного темпа.

Найденные времена долей дополнительно приближаются равномерной сеткой. На коротком и полном вариантах одной записи получилось следующее:

| Аудио | Долей | Fitted BPM | RMS отклонения | Максимальное отклонение |
| --- | ---: | ---: | ---: | ---: |
| 19,475 с | 47 | 145,9855 | 5,537 мс | 12,845 мс |
| 233,718 с | 564 | 145,9550 | 77,555 мс | 861,257 мс |

Средний темп почти одинаков, а соответствие одной глобальной сетке резко отличается. На результат влияют как временные изменения исполнения, так и ошибки beat tracker. Простой перенос среднего BPM на всю запись не учитывает эти отклонения.

В [analyze-rhythm.cjs](../speaker-player/converter/analyze-rhythm.cjs) fitted BPM используется при наличии хотя бы 8 долей, RMS не больше 20 мс и максимальном отклонении не больше 50 мс. В остальных случаях остаётся raw estimate. Для MIDI с изменениями темпа единая ритмическая сетка отключена, исходный таймлайн сохраняется.

Внешний MuScriptor MIDI может содержать marker `muscriptor:bar_offset`: начальную тишину, добавленную для выравнивания тактов. В исследованном файле 1,2634 секунды такого offset объясняли большую часть расхождения с аудио. Marker сохраняется отдельно; он не вычитается из каждого MIDI по умолчанию. [MuScriptor beats.py](https://github.com/muscriptor/muscriptor/blob/7f213afecf23bd6a1b8672aa223690ee9807cefb/muscriptor/utils/beats.py) описывает это выравнивание.

## Артикуляция без растягивания трека

Соседние ноты можно отделить короткой тишиной, подровнять к сетке или связать переходом высоты. Эти операции меняют уже распознанную мелодию. Разбиение одной строки на множество одинаковых отрезков не добавляет музыкальной информации и не повышает частоту дискретизации исходного MP3.

| Операция | Изменение |
| --- | --- |
| Транспонирование на `n` полутонов | `f' = f × 2^(n/12)`, время остаётся прежним |
| Скорость | Масштабирование временных границ |
| Note gap | Тишина из конца ноты |
| Quantize | Сдвиг внутренних границ на 50% к ближайшей клетке |
| Chop | Звук в заданной части каждой клетки |
| Glide | Переход высоты в начале следующей соседней ноты |

### Пауза берётся из ноты

Первоначальное добавление gap поверх длительности растягивало мелодию: каждая строка сдвигала все следующие. Теперь gap применяется после изменения скорости и забирает время из конца звучания:

```text
G = min(requestedGap, max(0, D − 1))
tone = D − G
pause = P + G
```

Для `D=100`, `P=20`, `G=10` получается 90 мс звука и 30 мс тишины. Следующая нота по-прежнему начинается через 120 мс. У непустого тона сохраняется хотя бы 1 мс; REST дополнительного gap не получает.

### Переход между высотами

Октава — удвоение частоты, поэтому glide интерполируется в логарифмической шкале. Cubic smoothstep задаёт плавную форму перехода:

```text
u ∈ [0, 1]
s(u) = 3u² − 2u³
f(u) = exp(log(f0) + (log(f1) − log(f0)) × s(u))
```

Переход занимает начало следующей ноты, ограничен её длительностью и не увеличивает время трека. На выходе это короткие удерживаемые частоты с интервалом обновления 5, 10, 20 или 50 мс. Первый и последний шаги соответствуют соседним высотам.

Glide действует между соприкасающимися звучащими нотами; реальная пауза, REST или note gap прерывают связь. Он применяется до Chop, чтобы искусственное дробление gate не создавало дополнительные музыкальные атаки.

Эффекты собраны в [SequenceTiming.cs](../speaker-player/src/SequenceTiming.cs). Его результат используется для графика, воспроизведения и сохранения обработанного CSV. После изменения скорости общая длительность равна `round(sourceTotal / speed)`. Quantize сохраняет порядок границ и типы REST, хотя меняет длины соседних интервалов; при округлении очень короткий интервал может исчезнуть.

## Как не накопить задержку к концу песни

Если каждый раз ждать длительность строки, а затем готовить следующую, расходы на output и обновление UI добавляются к музыкальному времени. Округление каждой длительности по отдельности создаёт вторую накопительную ошибку.

Плеер работает с абсолютными границами и одним monotonic clock:

```text
newBoundary[k] = round(sourceBoundary[k] / speed)
newDuration[k] = newBoundary[k+1] − newBoundary[k]
newTotal = round(sourceTotal / speed)
```

Каждый сегмент ждёт своего конца на общем таймлайне. Пользовательская pause исключается из clock. Seek переносит позицию, сохраняя выбранный backend и состояние pause.

`Stopwatch` измеряет время с высоким разрешением, но выполнение зависит от планировщика Windows. При опоздании короткая нота может получить меньше времени или быть пропущена. Разница между измерением времени и своевременным выполнением описана в документации Microsoft о [high-resolution timestamps](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps) и [Sleep](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-sleep).

После seek в UI очереди ещё может находиться progress callback со старой позиции. У запуска есть `SessionId`, а у смены позиции — `PositionRevision`; проверка выполняется внутри UI callback, перед обновлением экрана. Устройство этого взаимодействия описано в [разборе архитектуры](ARCHITECTURE.md). Программные тесты времени, событий и перемотки доступны в [руководстве по тестам](../speaker-player/tests/README.md).

Узнаваемая мелодия требует удачного выбора нот, корректного таймлайна и подходящего физического speaker. Проект делает эти этапы видимыми: полный MIDI хранит результат распознавания, CSV — выбранную линию и её время, диаграмма — последовательность частот. Так ошибки голоса, ритма и исполнения можно разбирать по отдельности.

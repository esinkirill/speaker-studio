# Исследование: музыка через speaker материнской платы

Этот документ описывает путь от одиночного аппаратного писка к Speaker Studio 2.0: распознаванию нот, одноголосной последовательности, ритмической обработке и воспроизведению. Он отделяет проверку файлов и программы от проверки физического звука и правильности мелодии.

Результаты зафиксированы 2 октября 2026 года. Исторические обозначения E09–E25 относятся к локальному журналу экспериментов. Исходная музыка, имена пользовательских файлов, машинные пути и необработанные журналы в этот документ не включены. Устройство программы описано в [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Что именно воспроизводит приложение

У физического PC speaker есть отдельный аппаратный путь. В этом проекте используется совместимый с legacy PC механизм: PIT channel 2 генерирует периодический сигнал, а gate включает и выключает его подачу на speaker. Наличие пищалки и писк при POST ещё не доказывают доступность этого пути из Windows на конкретной плате.

Приложение задаёт одну основную частоту за раз. У прямоугольного сигнала есть собственные гармоники, поэтому слово «одноголосный» здесь означает одну управляемую высоту, а не одну спектральную линию. Для нотной мелодии этого достаточно; исходные тембры инструментов при таком преобразовании теряются.

### Почему обычный Beep не решает задачу

Microsoft документирует изменение `Beep`: начиная с Windows 7 функция направляет сигнал на звуковое устройство по умолчанию для сеанса. Поэтому успешный `Beep` и звук из колонок не подтверждают управление speaker материнской платы. Это согласуется с наблюдением пользователя в ранних испытаниях проекта. [Microsoft: Beep](https://learn.microsoft.com/en-us/windows/win32/api/utilapiset/nf-utilapiset-beep).

Для прямого I/O выбран InpOut. Важная часть его устройства — kernel driver: DLL служит интерфейсом доступа к портам. Физический режим требует administrator и зависит от допуска драйвера системой. Это не решение исключительно встроенными средствами Windows. [Автор InpOut](https://www.highrez.co.uk/downloads/inpout32/).

## 2. Частота, делитель PIT и реальный излучатель

Реализация находится в [SpeakerOutput](../speaker-player/src/Playback.cs). Последовательность команд:

| Адрес | Действие приложения |
| --- | --- |
| `0x43` | Записать `0xB6`: channel 2, mode 3, binary count, low byte затем high byte |
| `0x42` | Записать два байта делителя |
| `0x61` | Включить младшие два gate/output бита, сохранив остальные |
| `0x61` при остановке | Очистить младшие два бита |

Mode 3 задаёт период прямоугольного сигнала. Для него допустимы counts от 2 до 65536; максимальный binary count кодируется двумя нулевыми байтами. Это подтверждено Figure 22 оригинального datasheet. [Intel 8254, mode 3 и Figure 22](https://www.cs.cmu.edu/~410/doc/8254.pdf).

В коде используется следующая модель legacy clock:

```text
clockHz = 1 193 182
count = clamp(round(clockHz / requestedFrequency), 2, 65536)
actualPitFrequency = clockHz / count
```

Отсюда **теоретический диапазон настройки таймера** составляет примерно **18,2 Гц — 596,6 кГц**. Он не является измеренным акустическим диапазоном пищалки. Нужный PIT путь может отсутствовать; излучатель, его резонанс и схема подключения имеют свои ограничения. Частота дополнительно квантуется целым делителем: диаграмма показывает подготовленные значения, а не измерение сигнала на пинах.

Старый предел 100–10000 Гц был ограничением программы, а не доказанным свойством InpOut. Его устранение расширяет команды, которые можно отправить таймеру, но не создаёт новый излучатель и не гарантирует слышимый результат на краях диапазона.

## 3. Почему MIDI и MP3 звучат по-разному

MP3 после декодирования даёт waveform — значения сигнала во времени. MIDI описывает нотные события и параметры музыкального исполнения. У него нет исходной формы каждого колебания. Speaker CSV ещё проще: частота, длительность, пауза.

```mermaid
flowchart LR
    A[MP3 / WAV] --> B[Декодирование]
    B --> C[Музыкальные события MuScriptor]
    C --> D[Полный MIDI с партиями]
    D --> E[Выбор партии и mono projection]
    E --> F[frequency / duration / pause]
    F --> G[PIT square wave]
```

Извлечь «дельту частот» нескольких инструментов и получить один эквивалентный тон нельзя: это не сохраняет их амплитуды, фазы и совместную waveform. Другой класс подходов — воспроизведение waveform через быстрые импульсы. Пример такого механизма есть в Linux `snd-pcsp`, где используется kernel hrtimer. Он не доказывает устойчивый PWM в нашем Windows player. [Linux: pcsp_lib.c](https://github.com/torvalds/linux/blob/master/sound/drivers/pcsp/pcsp_lib.c).

Эксперименты E09 с 1-bit/PDM проверяли математические файлы и запуск wrappers; физическое воспроизведение этим путём не проверялось. В релизе 2.0 используется нотный выход PIT, а старые waveform эксперименты не включены.

## 4. Распознавание и выбор одного голоса — разные задачи

Полный MIDI может содержать несколько нот одновременно даже в одной дорожке. Speaker Studio выбирает верхнюю активную ноту выбранной партии; если активных нот нет, получается REST. Повторный `note-on` выбранной высоты сохраняется как атака, даже если частота не изменилась. Событие более низкого сопровождения само по себе не разрывает удерживаемый верхний голос.

Такая проекция воспроизводима, но не определяет «главную мелодию». Верхний голос может оказаться сопровождающей партией, гармоникой или ошибкой распознавания. Исходный многоголосный MIDI сохраняется, поэтому другой selector можно исследовать отдельно.

В E22 в одном анонимизированном участке обнаружены 85 пар с общим началом и интервалом 19 полутонов:

```text
2^(19/12) ≈ 2,996614
```

Это близко к третьей гармонике. Но совпадение частот и атак не различает гармонику и реальную музыкальную партию. Автоматическое удаление всех таких нот было отвергнуто как достаточное решение. FFT peak также не является доказательством отдельной ноты или нужного голоса.

Для оценки нужны вручную подтверждённые pitch/onset/offset события и отдельное прослушивание. Подход к сопоставлению событий описан в [mir_eval transcription](https://github.com/mir-evaluation/mir_eval/blob/main/mir_eval/transcription.py).

## 5. Что сравнивалось в E23

На одном участке длиной около 19,475 секунды запускались разные ветви. Веса и параметры фиксировались; одни и те же декодированные данные использовались для основных сравнений. Это экспериментальная матрица на одном входе, а не оценка качества на репрезентативном датасете.

| Семейство | Базовых / контрольных вариантов | Что менялось |
| --- | ---: | --- |
| MIDI и его projections | 7 | Верхняя, нижняя, median и continuity/harmonic-aware линии |
| Спектральные методы | 12 | Каналы, harmonic salience, DP, фиксированные templates, HPSS |
| Melodia | 5 | Три extractor runs и варианты очистки |
| Basic Pitch ONNX | 14 | 8 canonical runs и 6 отдельно помеченных decoder controls |
| YourMT3 | 10 | 5 checkpoints, прямой запуск и сдвинутая сетка окон |
| MuScriptor Small | 4 | Default, shift, отключение prelude, CFG 2 |
| Consensus | 2 | Пересечение согласованных событий двух запусков |
| **Всего базовых / контрольных** | **54** | |
| Производные mono selectors | **90** | Highest, lowest, harmonic DP для 30 polyphonic candidates |
| **Всего вариантов** | **144** | |

Разделение Demucs использовалось как предварительная аудиообработка: mix/other/bass и дополнительные stems. Stem `other` не гарантирует выделенный lead. Basic Pitch и Demucs выполняют разные задачи: первое распознаёт события, второе разделяет аудио. [Basic Pitch](https://github.com/spotify/basic-pitch), [Demucs](https://github.com/facebookresearch/demucs).

Спектральная ветвь с фиксированными Gaussian templates и неотрицательными коэффициентами — fitting при заданном `W`, а не blind learned NMF. Более гладкая линия может быть неправильной; меньший остаток спектральной реконструкции также не доказывает принадлежность главному голосу.

### Agreement не равно accuracy

При сдвиге аудио сравнивались два предсказания одной модели: тот же pitch, onset в пределах 50 мс; для строгого сравнения учитывался offset. Полученное agreement характеризует устойчивость к контексту и разбиению:

| Модель / конфигурация | Onset agreement F1 |
| --- | ---: |
| YourMT3 Single | 0,890 |
| YourMT3 T5 | 0,535 |
| YourMT3 MoE | 0,461 |
| YourMT3 MultiPS | 0,664 |
| YourMT3 MoEPS | 0,333 |
| MuScriptor Small | 0,685 |

Два запуска могут согласованно ошибаться. Consensus сохранил 71 из 96 событий Single и 110 из 197 MuScriptor, но правильность удаления остальных неизвестна. Число нот, число переключений и сравнение с другим неподтверждённым MIDI не выбирают лучший алгоритм автоматически.

## 6. Почему в production выбран MuScriptor Small

Пользователь сообщил, что понравившийся ему MIDI получен через MuScriptor. Его конкретный сервисный checkpoint не установлен; локальный Small не объявляется идентичным ему. Выбор Small позволяет получить отдельную локальную ветвь и CPU workflow с известными файлами и параметрами.

MuScriptor предсказывает события нот и инструментов по mel-spectrogram. Используемая версия обрабатывает mono 16 кГц фрагментами по 5 секунд; prelude переносит состояние удерживаемых нот между фрагментами. Это модельная гипотеза музыкальных событий, а не извлечение готовой партитуры без ошибок. [Зафиксированный source revision](https://github.com/muscriptor/muscriptor/blob/7f213afecf23bd6a1b8672aa223690ee9807cefb/muscriptor/transcription_model.py).

В production wrapper используются local weights, CPU, greedy decoding, `cfg_coef=1`, `prelude_forcing=True`, `batch_size=1`. Полный MIDI сохраняет партии и percussion; MIDI → speaker CSV отдельно исключает percussion и делает mono projection. Экспортная velocity фиксирована на 64: динамика исходного исполнения не восстановлена.

Код MuScriptor имеет MIT license, веса Small — CC BY-NC 4.0 и условия доступа автора. Общая лицензия приложения не заменяет лицензии зависимостей и модели. [Официальная model card и условия](https://huggingface.co/MuScriptor/muscriptor-small).

## 7. BPM, сетка и «дискретизация»

Это три разных операции:

| Операция | Что определяет |
| --- | --- |
| Оценка BPM по аудио | Предположение о долях и их временах |
| Музыкальная сетка | Равные части доли с заданной фазой |
| Шаг glide | Как часто меняется управляемая частота перехода |

Для BPM, определённого относительно четверти:

```text
sourceStepMs = 60000 / sourceBpm / partsPerBeat
playbackStepMs = sourceStepMs / speed
grid[k] = phaseMs + k × sourceStepMs
speed = desiredBpm / sourceBpm
```

Например, при 120 BPM и четырёх частях четверти шаг равен 125 мс — шестнадцатой ноте. Деление 16 даёт 1/64, а не шестнадцатую. Фаза нужна для расположения клеток на таймлайне; одна величина BPM не определяет начало доли.

Essentia `RhythmExtractor2013` возвращает BPM и найденные доли. Его confidence не является вероятностью правильного BPM; возможны половинный или двойной темп. [Документация Essentia](https://essentia.upf.edu/reference/std_RhythmExtractor2013.html).

В E20 короткий участок дал 47 долей: raw 145,1553 BPM, fit 145,9855 BPM, RMS 5,537 мс. Для полного аудио около 233,718 секунды fit 145,9550 BPM имел RMS 77,555 мс и максимум 861,257 мс. Близкий средний BPM не подтвердил равномерную сетку всего трека.

Отдельно учитывается MIDI marker `muscriptor:bar_offset`: некоторые внешние MIDI добавляют тишину для выравнивания тактов. В исследованном примере offset 1,2634 секунды объяснял большую часть различия длительностей. Это свойство конкретного файла, не универсальная поправка. Обработка offset и ритма видна в [MuScriptor beats.py](https://github.com/muscriptor/muscriptor/blob/7f213afecf23bd6a1b8672aa223690ee9807cefb/muscriptor/utils/beats.py).

Увеличение числа одинаковых частотных строк не добавляет музыкальных сведений. Разрывы изменяют артикуляцию; glide добавляет выбранный переход высоты. Они не восстанавливают пропущенные ноты и не повышают частоту дискретизации исходного MP3.

## 8. Ритм и плавные переходы в приложении

Общий расчёт находится в [SequenceTiming.cs](../speaker-player/src/SequenceTiming.cs): одинаковые подготовленные события используются для диаграммы, проигрывания и экспорта.

| Параметр | Реализованное действие | Что сохраняется |
| --- | --- | --- |
| Тон, полутоны | `f' = f × 2^(n/12)` | Длительность |
| Скорость | Масштабирование абсолютных временных границ | Относительный ритм и tempo changes |
| Note gap | Вырезать тишину из конца ноты, прибавить её к паузе | Начало следующей ноты и длина трека |
| Quantize | Переместить внутренние границы на 50% к ближайшей клетке | Общая длина, порядок; REST остаётся REST |
| Chop | Пересечь звучащие интервалы с сеткой «звук / тишина» | Общая длина, исходная тишина |
| Glide | В начале следующей соседней ноты менять log-frequency по smoothstep | Общая длина и настоящие паузы |

Quantize может перемещать границы пауз и менять их длину; очень короткий участок может исчезнуть при округлении до миллисекунд. Это не обещание сохранить каждый onset или pause duration неизменным.

Для gap после масштабирования времени:

```text
G = min(requestedGap, max(0, D − 1))
tone = D − G
pause = P + G
```

При `D=100`, `P=20`, `G=10` получается 90 мс звука и 30 мс паузы; сумма остаётся 120 мс. Первоначальное добавление паузы поверх ноты удлиняло трек и было исправлено в E19.

Glide использует музыкально равномерное пространство высот:

```text
u ∈ [0, 1]
s(u) = 3u² − 2u³
f(u) = exp(log(f0) + (log(f1) − log(f0)) × s(u))
```

Получается последовательность коротких удерживаемых частот с шагом 5/10/20/50 мс. Это приближение, а не непрерывный аналоговый генератор. Glide не проходит через REST, исходную паузу или note gap и применяется до искусственного Chop.

## 9. Почему нет ползунка напряжения

Текущий hardware backend управляет делителем и gate. В этом интерфейсе нет независимого регистра аналоговой амплитуды. Переписывание DLL не создаёт такой регистр. Поле «Звук, %» означает долю времени звучания клетки и не обещает пропорциональную громкость. [Intel: NMI Status and Control, offset 61](https://edc.intel.com/content/www/ru/ru/design/products-and-solutions/processors-and-chipsets/comet-lake-u/intel-400-series-chipset-on-package-platform-controller-hub-register-database/1.2/nmi-status-and-control-nmi-sts-cnt-offset-61/).

Для отдельных external-drive piezo возможны аппаратные способы ослабления, но сначала нужны тип излучателя и схема подключения. Номинал резистора для неизвестного speaker в проекте не назначался. [Murata: регулировка sound pressure внешнего piezo](https://www.murata.com/en-global/support/faqs/sound/diaphragm/char/sch0001).

Высокочастотный PWM/PDM, акустическое измерение громкости и аппаратный регулятор остаются отдельными неподтверждёнными направлениями. В релиз они не входят.

### Ошибка исходной portability-гипотезы

Изоляция Python и `PATH` не изолируют весь Windows DLL loader. Первоначальный комплект успешно загружал модель, используя `msvcp140.dll` из системы, хотя этой DLL в комплекте не было.

Исправление: добавлен app-local MSVC runtime 14.51.36231.0, проверены ordinary и delay imports 83 Python native images, отдельно Node/FFmpeg. Новый процесс реально загрузил все три VC14 DLL из комплекта; Microsoft signatures проверены. Затем комплект перепакован и проверен повторным C# smoke. Чистая Windows VM всё ещё не запускалась.

## 11. Воспроизводимость и границы доказательств

Источники результатов — локальный журнал E09–E25 и отдельные reader, timing, GUI, process, native dependency и package reports. Они содержат приватные пути и музыкальные входы, поэтому необработанные файлы не публикуются здесь. Приведённые числа — исторические результаты проверенного локального комплекта, а не автоматический результат `git clone`.

Для независимого повторения нужен аудиоматериал с подходящими правами, фиксированные model/source revisions, параметры декодера и selector, а также сохранённые intermediate MIDI/events. Проверять следует отдельно:

1. Валидность данных и повторяемость экспорта.
2. Pitch/onset/offset относительно ручной разметки.
3. Узнаваемость и артикуляцию при A/B.
4. Физический звук на конкретной плате.
5. Timing и автономность на другой Windows конфигурации.

## 12. Следующие эксперименты

| Гипотеза | Проверка | Критерий результата |
| --- | --- | --- |
| Highest selector выбирает лишние harmonics | Разметить 15–30 нот, сравнить highest/lowest/harmonic DP | Pitch/onset/offset ошибки и пропуски, отдельно A/B |
| Prelude/shift consensus помогает стыкам | Сдвигать окна на одном входе и проверять reference | Уменьшение ошибок без потери настоящих атак |
| Grid улучшает артикуляцию | Original против Quantize и Chop при одинаковой длине | Проверенная длительность плюс оценка человека |
| Glide слышим и управляем | Переход 0 и 80 мс, шаг 10 мс, gap 0 | Слышимый результат на свободном целевом ПК |
| Portable closure достаточна | Чистые Windows 10/11 x64 VM, затем отдельная плата | Локальная конвертация без системного VC runtime; отдельно hardware sound |
| Громкость можно ослабить аппаратно | Определить излучатель и схему, затем измерить выбранное решение | Измеренный эффект; без универсального номинала |

До этих проверок приложение остаётся исследовательским инструментом с проверенной программной цепочкой и конкретными аппаратными ограничениями.
